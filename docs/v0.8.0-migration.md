# v0.8.0 Migration Notes

v0.8.0 keeps the public Portal MCP behavior compatible with v0.7.9 while adding internal and enterprise endpoint, hosted auth, readiness, and observability controls.

## Public And Self-Hosted Defaults

No change is required for a local stdio setup or a public HTTP setup that uses the default SQD Portal endpoint.

- `PORTAL_URL` is still supported and now maps to the default `PortalEndpoint`.
- If no MCP HTTP auth is configured, `POST /` and `POST /mcp` remain anonymous outside strict readiness mode.
- `/health`, `/ready`, `/tools`, and `/tools.json` remain public and safe.

## Endpoint Configuration

For standard same-origin SQD dedicated portals, do not enumerate customers. Route `https://<customer-slug>.portal.sqd.dev/mcp` to the central MCP service and preserve `Host`; the MCP service derives `portalBaseUrl=https://<customer-slug>.portal.sqd.dev` dynamically and requires delegated Portal API-key auth for that host. `https://portal.sqd.dev/mcp` remains the anonymous public endpoint.

For one non-standard dedicated endpoint, keep using `PORTAL_URL` and add safe endpoint metadata:

```bash
PORTAL_BASE_URL=https://upstream.portal.example.com
PORTAL_ENDPOINT_ID=enterprise-prod
PORTAL_MCP_HOSTNAMES=dedicated.portal.example.com
PORTAL_ENDPOINT_LABEL="Enterprise production"
PORTAL_ENDPOINT_CLASS=enterprise
PORTAL_ENDPOINT_TENANT_SCOPE=tenant
PORTAL_ENDPOINT_TENANT_ID=tenant_example
PORTAL_ENDPOINT_AUTH_MODE=bearer
PORTAL_ENDPOINT_TOKEN_ENV=ENTERPRISE_PORTAL_TOKEN
```

For multiple non-standard endpoints, use `PORTAL_ENDPOINTS` and `PORTAL_DEFAULT_ENDPOINT_ID`.

Endpoint classes are limited to `public`, `internal`, and `enterprise`. `public` is the unauthenticated `https://portal.sqd.dev` endpoint. `internal` is for SQD-operated API-key endpoints configured outside this public repo. `enterprise` is for customer-dedicated API-key endpoints configured outside this public repo.

Do not put credentials, real customer hostnames, or real customer identifiers in this public repo. Reference secret environment variables with `tokenEnv` / `PORTAL_ENDPOINT_TOKEN_ENV`, and set real endpoint config only in the deployment environment or secret manager.

Hosted deployments can keep the MCP URL on the same portal origin by routing `https://<portal-host>/mcp` through the portal edge to one central MCP service. Preserve `Host`, or set `MCP_TRUST_FORWARDED_HOST=true` and pass the original portal host as `X-Forwarded-Host`, so MCP can select the correct deployment-only `PortalEndpoint`.

Internal and enterprise endpoint URLs must use HTTPS. Dataset availability is defined by the selected Portal endpoint's `/datasets` response, not by MCP key metadata.

## MCP Auth

Self-hosted deployments can keep using:

```bash
MCP_HTTP_BEARER_TOKEN=<static-mcp-token>
```

Hosted deployments should use portal-app issued MCP key records:

```bash
MCP_AUTH_KEYS='[
  {
    "id": "mcpkey_01j...",
    "audience": "portal-mcp",
    "tokenSha256": "64 lowercase hex characters",
    "principalId": "user_123",
    "tenantId": "tenant_example",
    "endpointId": "enterprise-prod",
    "scopes": ["mcp:invoke"],
    "credentialPolicy": "tenant_portal_endpoint",
    "status": "active"
  }
]'
```

The browser portal-app session token `sqd.portal.authToken` must not be used as an MCP runtime credential. See [Portal App MCP Auth Contract](portal-app-mcp-auth-contract.md).

If portal app changes are out of scope, hosted deployments can instead use the built-in delegated Portal API-key bootstrap:

```bash
MCP_DELEGATED_AUTH=true
PORTAL_ENDPOINTS='[
  {
    "id": "sqd-internal",
    "portalBaseUrl": "https://upstream.portal.example.com",
    "mcpHostnames": ["sqd.portal.example.com"],
    "label": "SQD internal Portal",
    "endpointClass": "internal",
    "tenantScope": "tenant",
    "tenantId": "sqd",
    "authMode": "delegated_api_key",
    "headerName": "x-api-key"
  }
]'
```

Users connect to `https://<portal-host>/mcp` in a compatible MCP client. The client follows the MCP OAuth discovery flow, opens the hosted Portal API-key form, exchanges the authorization code for the MCP access token, and resumes automatically after the user pastes their Portal API key once. In production, leave `MCP_DELEGATED_AUTH_VALIDATE` enabled so the key is checked against the selected Portal endpoint's `/status`.

## Readiness And Metrics

Set these in hosted or production HTTP deployments:

```bash
MCP_READINESS_STRICT=true
MCP_CURSOR_SECRET=<deployment-specific-secret>
METRICS_BEARER_TOKEN=<metrics-token>
```

- `/health` is liveness only and should stay 200 if the process is up.
- `/ready` reports endpoint config, cursor signing, MCP auth, metrics protection, and Portal reachability.
- `/ready` returns 503 when a required strict check fails.
- `MCP_READY_CHECK_PORTAL=false` disables the live Portal probe when the platform already has upstream health checks.

## Observability

Tool events now include safe endpoint and auth context:

- `endpoint_id`, `endpoint_class`, `endpoint_auth_mode`
- hashed `endpoint_tenant_key` when a tenant id is configured
- `mcp_auth_mode`, `mcp_auth_outcome`, and bounded `credential_policy`
- `request_id`, `invocation_id`, and upstream Portal status summaries

Tool events must not include raw principal ids, tenant ids, key ids, bearer values, or outbound Portal credentials.
